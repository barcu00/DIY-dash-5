# OpenDash v0.2 Render-Parity UI Design

**Date:** 2026-09-02
**Status:** Proposed for implementation after user review
**Target:** Waveshare ESP32-S3-Touch-LCD-5, 800x480, non-B
**UI stack:** LVGL 8.4 on Arduino-ESP32

## Goal

Rebuild the OpenDash v0.2 presentation layer so the real 800x480 display matches the approved dashboard render as closely as practical, while preserving the already-working CAN, ECUMaster decoder, Parameter Registry, Alarm Manager, NVS configuration, tile editor, and data-source architecture.

The reference render is the visual source of truth for proportions, hierarchy, density, panel treatment, typography, icon style, and screen composition. The existing `ui.cpp` implementation is not a visual source of truth and may be replaced or split where needed.

## User-approved deviations from the reference render

1. Remove the OpenDash logo/header strip entirely.
2. Remove clock, Wi-Fi, CAN badge, and battery voltage from the header.
3. Use the recovered top space for a permanent full-width RPM/shift-light indicator.
4. Do not add bottom navigation dots or page-number indicators.
5. CAN state and battery voltage remain available as normal configurable parameters and on DIAG.

## Non-goals

- Do not change ECUMaster frame decoding or CAN electrical configuration.
- Do not implement fake lap times, fake track maps, fake GPS traces, or fake diagnostic states.
- Do not silently fall back from a real ECU source to MOCK when CAN data is stale.
- Do not add Wi-Fi, RTC, GPS, SD logging, or audio alarms in this redesign unless already backed by real runtime data.
- Do not use a static screenshot as the dashboard background. Every value and state remains a real LVGL object.

## Visual target

### Global visual language

- Resolution: exactly 800x480 landscape.
- Background: near-black blue/graphite.
- Panels: slightly lighter blue-black with a subtle 1 px cool-gray border.
- Corners: 7-10 px radius, not heavily rounded.
- High contrast white numeric values.
- Muted gray labels and units.
- Parameter icons use a simple automotive line style with 2-3 px apparent stroke weight.
- Icon color is semantic and restrained: cyan/blue for general sensors, green for healthy/coolant/fuel-active states, amber for oil/ignition, purple for lambda/AFR, red for errors/critical values.
- Avoid gradients, large shadows, glossy effects, and decorative elements that reduce readability.

### Typography

Use a narrow, high-legibility embedded LVGL font instead of relying only on the current built-in Montserrat sizes. Preferred family: **Roboto Condensed** (Apache-2.0), converted to LVGL C assets and stored in the repository; only required glyphs are generated.

Required roles:

- tile title: 14 px condensed semibold
- tile value: 32-36 px condensed medium/bold
- tile unit: 13-14 px condensed regular
- screen heading: 24-28 px condensed semibold
- secondary/status text: 13-16 px condensed
- top RPM numeric: 28-32 px condensed bold

Required glyphs include ASCII plus `°` and other units actually used by the Parameter Registry.

## Dashboard geometry

### Permanent RPM / shift-light strip

The top **48 px** of every DASH page are reserved for the RPM indicator.

- 12 shift-light segments.
- Horizontal margins: approximately 12 px.
- Segment spacing: approximately 6 px.
- Segment height: 10-12 px.
- Segment colors by RPM progression: inactive graphite -> green -> amber -> red.
- RPM numeric centered below the segments inside the same 48 px region.
- RPM strip uses the real `ParameterId::Rpm` value.
- The strip stays visually identical on DASH 1, DASH 2, and DASH 3.
- Future alarm/limiter behavior may flash red segments, but basic RPM indication must work independently of warning configuration.

### DASH page tile area

Below the 48 px RPM strip, each DASH page contains exactly **12 tile slots in a 4 column x 3 row grid**.

Target geometry:

- left/right margin: 8 px
- top of tile grid: y = 52 px
- bottom margin: 8 px
- horizontal gap: 6 px
- vertical gap: 6 px
- tile width: 191 px
- tile height: approximately 134 px

The geometry must be centralized in a testable layout model. No independent hard-coded positions scattered through `Ui::createDash()`.

### Tile anatomy

Each tile follows the reference render hierarchy:

1. parameter label at top-left;
2. semantic icon at lower-left;
3. large value in the primary visual area;
4. small unit adjacent to or below the value;
5. warning state expressed by border/value/icon color, not by replacing the value with decorative UI.

Recommended internal geometry for a 191x134 tile:

- title: x=12, y=9
- icon box: 30-32 px, x=12, y=52
- value: x=54-58, y=38-44
- unit: aligned close to the value baseline or directly below value depending on text width

Values must not collide with icons or units for normal Parameter Registry ranges. Long labels are clipped/ellipsized rather than shrinking the value font.

### Icon assets

Replace per-tile 16x16 true-color canvas rendering with reusable **28-32 px monochrome alpha-mask image assets** (`LV_IMG_CF_ALPHA_1BIT` or another memory-efficient LVGL alpha format). Recolor the same asset at runtime using LVGL image recolor/style properties.

Benefits required by this design:

- sharper icons at physical 5-inch viewing distance;
- render-like proportions;
- no 32x32 true-color buffer per tile;
- one static asset per semantic icon family;
- deterministic memory use;
- runtime warning/status recolor without redrawing a canvas bitmap.

Every `ParameterId` continues to have a default semantic `IconId`; related parameters may intentionally share a symbol.

## DASH page model

OpenDash exposes three dashboard pages:

- `Dash1`
- `Dash2`
- `Dash3`

Each page has 12 independent configurable tile slots, for a total of **36 DASH tile configurations**.

The existing two-profile model (`tiles` and `track_tiles`) is insufficient for this layout. Persistent configuration must migrate to a schema that stores three DASH profiles plus the TRACK configuration.

### Default parameter allocation

Defaults should visually follow the reference render while using only parameters that actually exist in the registry.

**DASH 1 defaults:**
RPM, Vehicle Speed, Boost/MAP-derived pressure choice, MAP, IAT, CLT, Oil Temperature, Oil Pressure, Lambda shown as AFR, Lambda, Ignition Angle, TPS/Throttle.

**DASH 2 defaults:**
Fuel Pressure, Battery Voltage, Injector Pulse Width, injector/load-related available values, knock, EGT, Gear, DBW/torque/traction values where available.

**DASH 3 defaults:**
remaining diagnostic/auxiliary values such as barometric pressure, analog channels, PWM outputs, switches, fuel used, ECU temperature, sensor states, and other registry parameters.

No unavailable concept from the render (for example altitude or trip distance if not backed by the current registry) may be fabricated merely to match the picture.

## TRACK screen

TRACK follows the reference composition rather than the current central RPM/gear panel.

- Left approximately 70%: track/map area.
- Right approximately 30%: BEST LAP, LAST LAP, DELTA stack.
- Bottom: SPEED, RPM, GEAR summary values.
- If there is no real lap/GPS source, track area shows a restrained `NO TRACK DATA` / `GPS NOT AVAILABLE` state.
- Lap values show `--:--.--` until real data exists.
- No synthetic track outline and no synthetic lap timing.

TRACK remains a top-level horizontally navigable screen.

## DIAG screen

DIAG uses the compact list/table visual language from the render instead of large oversized status cards.

Rows:

- DTC / ECU error state
- CAN status
- sensor status summary
- data source
- uptime
- memory / heap
- display/touch status
- received frame count
- invalid frame count

Healthy status uses green, waiting/degraded uses amber, failure uses red. Values come only from existing runtime diagnostics and registry state.

## SETTINGS screen

SETTINGS follows the render: a clean vertical row list, not large cards.

Minimum entries:

- DASH LAYOUT
- TRACK LAYOUT
- PARAMETERS
- UNITS / FUEL-AFR
- ALARMS / WARNINGS
- CAN
- SYSTEM
- ABOUT

Vertical drag scrolls the list. Horizontal swipe still navigates away from SETTINGS because horizontal page navigation no longer depends on LVGL's built-in `LV_EVENT_GESTURE`.

## Parameter and tile editing

### DASH LAYOUT

- Select one of Dash1/Dash2/Dash3.
- Navigate all 12 slots, including hidden slots.
- Hidden tiles remain recoverable with `SHOW TILE`.
- Long-press on a visible tile opens the same editor directly.
- No instructional `Long press a tile to edit` text appears on the dashboard.

### Parameter editor

Match the reference visual hierarchy:

- preview tile at top;
- parameter choice;
- position/slot;
- icon choice/default/off;
- visible/hidden;
- decimals;
- Lambda/AFR when eligible;
- SAVE/CANCEL or equivalent explicit exit behavior.

The existing safe asynchronous LVGL overlay lifecycle must be retained; an event callback must never synchronously destroy the object currently dispatching that event.

## Navigation model

### Root page ring

Horizontal swipes navigate this ring:

`Dash1 -> Dash2 -> Dash3 -> Track -> Diag -> Settings -> Dash1`

Right swipe traverses the same ring in reverse.

There are no bottom dots, persistent navigation buttons, or page-number labels.

### Raw-touch swipe recognition

Production navigation must stop depending on LVGL `LV_EVENT_GESTURE`.

A pure C++ `TouchSwipeRecognizer` receives raw GT911 press/move/release samples from `BoardDisplay::touchCallback()` and emits one of:

- Left
- Right
- None

Rules:

- minimum horizontal travel: 70 px
- maximum swipe duration: 700 ms
- horizontal distance must be greater than vertical distance by a configurable dominance margin (initial target: `abs(dx) >= abs(dy) * 1.25`)
- vertical movement does not change page
- long press does not change page
- a recognized horizontal swipe is emitted once on release
- touch coordinates use the native 800x480 orientation; current board config has no X/Y swap or mirror

The recognized swipe is queued by `BoardDisplay` and consumed by `App`, which calls `Ui::handleSwipe(direction)` under the LVGL lock.

`Ui::handleSwipe()` ignores root-page navigation while a modal tile/settings editor is active.

This architecture makes the production code use the same swipe classifier that is covered by native tests.

## Persistent configuration and migration

Current NVS namespace remains `opendash`.

Increment schema version because 36 DASH slots change the persistent structure.

Migration policy:

- preserve CAN source, bitrate, base ID, timeout, stoich AFR, parameter visibility, warnings, and other compatible settings;
- map the existing 12 DASH tiles into Dash1;
- initialize Dash2 and Dash3 from new defaults;
- preserve existing TRACK tile settings when structurally compatible;
- if legacy data cannot be safely migrated, factory-default only the incompatible UI-layout portion rather than corrupting unrelated CAN/warning settings;
- no large `AppConfig` temporary objects on the Arduino task stack.

## Alarm presentation

Existing Alarm Manager remains the source of truth.

For each tile:

- Normal: standard border/value/icon colors.
- Warning: amber border and value emphasis.
- Critical: red border and value emphasis.
- Invalid/offline: muted value `---`, no false warning coloration.

Do not make parameter visibility suppress warning evaluation.

## Memory constraints

The current application already uses a substantial fraction of internal RAM, so render parity must not be implemented by multiplying true-color canvas buffers.

Requirements:

- reusable static icon alpha assets;
- no full-screen background bitmap;
- no per-tile true-color icon canvas;
- avoid constructing all modal editors until opened;
- retain LVGL memory monitoring in diagnostics;
- firmware must remain below ESP32-S3 internal RAM limits with practical free heap after startup.

If creating all six top-level screens simultaneously becomes too expensive, DASH pages may share a reusable page component or screens may be lazily created, but user-visible transitions must remain immediate.

## Code organization

The current `src/ui/ui.cpp` is too large for this redesign. Split responsibilities while preserving the public `Ui` facade.

Recommended units:

- `src/ui/ui_theme.h/.cpp` - colors, fonts, dimensions, common styles
- `src/ui/touch_swipe_recognizer.h/.cpp` - pure swipe state machine
- `src/ui/dash_layout.h/.cpp` - deterministic 4x3 geometry and page/slot mapping
- `src/ui/tile_widget.h/.cpp` - one render-parity tile component
- `src/ui/shift_light_widget.h/.cpp` - top RPM/shift-light component
- `src/ui/ui_dash.cpp` - Dash1/Dash2/Dash3 creation/update
- `src/ui/ui_track.cpp` - TRACK creation/update
- `src/ui/ui_diag.cpp` - DIAG creation/update
- `src/ui/ui_settings.cpp` - SETTINGS creation/update
- `src/ui/ui.cpp` - orchestration, page loading, editors, root navigation
- `src/board/board_display.*` - raw touch sample capture and pending swipe queue only
- `src/app/app.cpp` - consumes pending swipe and invokes `Ui` under LVGL lock

Do not move CAN or decoder logic into UI files.

## Testing requirements

### Native tests

Add tests before implementation for:

1. exact 4x3 DASH geometry stays inside 800x480 and does not overlap the 48 px RPM strip;
2. page ring includes Dash1/Dash2/Dash3/Track/Diag/Settings and wraps both directions;
3. raw swipe recognizer accepts valid left/right swipes;
4. recognizer rejects vertical, short, and long-duration movements;
5. only one navigation event is emitted per gesture;
6. 36 DASH slots persist and remain independently configurable;
7. migration maps old 12 DASH tiles to Dash1 without losing CAN/warning configuration;
8. every ParameterId has a valid reusable icon asset;
9. hidden slots can be reached and restored;
10. invalid/stale values render as `---` without false alarms.

### Firmware build

CI must pass:

- all native tests;
- Waveshare ESP32-S3 firmware build;
- merged full image creation;
- artifact upload.

### Hardware acceptance

On the physical Waveshare display:

1. Dash1 visually matches the approved render proportions, icon hierarchy, typography, and density, except for the approved RPM/shift-light header replacement.
2. Shift-light and RPM update smoothly from MOCK and real ECUMaster data.
3. Left/right swipe reliably traverses all six root pages.
4. SETTINGS still scrolls vertically.
5. Long press opens the correct tile editor without accidental page change.
6. Three DASH pages retain independent layouts after restart.
7. Hidden tiles are recoverable.
8. No duplicated/tearing overlay graphics after repeated edits.
9. No black-screen regression after NVS save/restart.
10. Real CAN timeout shows stale data as `---`/offline without MOCK fallback.

## Definition of done

The redesign is complete when the physical 800x480 device, not only a concept render, exhibits the approved render's visual structure and density; the top region is an RPM/shift-light instead of a branding/status bar; all root pages are reachable by reliable raw-touch horizontal swipes; three independent 12-tile DASH pages are persistent and editable; and all existing CAN/ECU/NVS/alarm tests and hardware behaviors remain intact.
